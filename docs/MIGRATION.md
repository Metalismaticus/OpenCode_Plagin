# Переход и пилот

Сборка предназначена для OpenCode V2. В основе — исходный CLAUDE_Game,
а прежний OpenCode-порт использован для платформенных адаптаций и телеметрии.
Оригинальный репозиторий CLAUDE_Game не меняется.

## Существующий проект

1. Сохранить текущую работу обычными средствами проекта и закрыть активный
   запуск партии. Не смешивать незакоммиченный код с миграцией процесса.
2. Выполнить install.py/install.ps1 из новой сборки. Установщик оставляет
   настройки провайдеров и чужие плагины, предыдущие заменяемые файлы сохраняет
   в `../<проект>.wt/install-backups/`. Без предыдущего install-manifest он
   ничего рекурсивно не удаляет; старые неизвестные агенты могут остаться.
3. Перечитать плагин в OpenCode и открыть новый чат с агентом studio.
   `/studio/setup обновить` сохраняет собственные решения/замысел/очередь,
   обновляет процессные разделы по исходному протоколу.
4. Незакрытая прежняя BATCH — сверка с git и новой карточкой, независимым
   reviewer и проверками. Не мигрировать строку «одобрен» сразу в accepted.

Не удалять `../<проект>.wt/state/`: там история новых задач, режимы сессий,
подтверждённые стадии и фактические результаты checks. Новая сессия
разработки может `adopt` задачу после наблюдаемого указания владельца.
Подвисшую проверку восстанавливает `recover` только когда её процесс мёртв.
После аварии с workflow.lock проверить записанный pid и отсутствие процесса;
не снимать блокировку у живого писателя.

## Первый живой прогон

Начать на отдельной копии игры с тремя небольшими реальными задачами:

- очевидный баг с воспроизводимым симптомом и применимой проверкой;
- маленькая фича, объяснённая словами игрока;
- видимая поправка по вашему кадру, с местом/seed/временем и сравнением.

Наблюдать: понял ли ИИ смысл; обоснованы ли файлы; реально ли исполнился Flash;
независим ли reviewer; сохраняются ли причина отказа и следующий шаг после
обрыва; можно ли увидеть результат там, где вы проверяете его; сколько
потреблено по исходной телеметрии. Потом — один намеренный отказ в `/done`,
проверка фактического revert и повтор с дословной причиной.

Только после этого испытывать большую систему и параллельную волну. Эти
сценарии проверяют качество постановки задач и GLM, чего unit-тесты не измеряют.

## Проверенные границы

- Runtime сохраняет и проверяет стадии, но **не является второй LLM**:
  понимание вкуса, хорошие архитектурные решения и содержательность ревью
  всё ещё зависят от выбранных моделей и исходников.
- Ролевые edit-права и concept-shell ограничения реализованы в плагине.
  Shell работает с полномочиями пользователя; процессный guard не заменяет
  ОС sandbox. Отключение плагина или переключение на свободный build-агент
  выводит работу из этого workflow.
- `verify` исполняет заданные карточкой команды. Их должен выбрать coordinator
  по TESTING.md; ноль checks допускается только с явным verification_limit.
  Поэтому verified означает прохождение **заявленных** проверок, не доказанное
  качество всех систем, визуальное сходство или удовольствие от игры.
- Подтверждение владельца хранится из prompt/question, а не из утверждения
  агента. Истолкование частичных «кроме/только» остаётся обязанностью
  acceptance-контроллера по исходному протоколу; показываются конкретные пункты.
- Отказ — запись решения. Revert, проверка итогового продукта, документы и
  закрытие BATCH выполняются исходным acceptance workflow отдельно.
- Исходные протоколы перенесены без нового перевода; русский здесь намеренный.
  Экономия достигается выборочной загрузкой. Проценты экономии токенов и
  равенство с Opus не заявляются без живого измерения.
- V2 API сверялось с официальными разделами
  [plugins](https://opencode.ai/v2/docs/build/plugins),
  [permissions](https://opencode.ai/v2/docs/permissions),
  [agents](https://opencode.ai/v2/docs/agents) и
  [tools](https://opencode.ai/v2/docs/tools).
  Адаптер проверен на контрактном стенде, а не на вашем запущенном сервисе.

## Где изменять

Роли/права: build/roles.json → configure.py.
Модели: build/models.json → configure.py.
Контроллеры: studio-development/planning/acceptance в skills.
Переходы/контракты: studio/runtime. Правило движка: соответствующий skill.
Исходные главы: менять источник/PIN и заново сверять importer; не редактировать
генерируемый protocol вручную, иначе check_integrity обнаружит расхождение.
